00 · MASTER API / TRUST ZONES

Public reads are first-class — but public DTOs are not raw database rows

Cloudflare fronts all internet traffic. Public read endpoints can be cached where safe. Authenticated player, owner and admin APIs use JWT + scoped RBAC. Tokenized QR payment is public only through an expiring capability. Provider webhooks are internet-facing but cryptographically trusted, not “public API”.

Public data

Cities, active venue details, availability views, reviews, extras, team profiles, fixtures, standings and tournament browse.

Never public

User PII, owner payout method, internal venue notes, disputes, full booking records, provider refs and admin/staff data.

Notifications

Push + email by default. Email adapter can use Resend or Cloudflare Email Sending. SMS is OTP/critical fallback.

Payouts

Per-venue cadence. Default weekly; daily can be enabled for eligible settled/completed money after cutoff.

API ACCESS SURFACE

Every endpoint is labelled by trust level

“Public” means intentionally safe to expose without a user session — not a direct table dump. All public responses should use whitelisted response DTOs, pagination and rate limits. Writes remain protected by auth, capabilities or provider signatures.

01 · SEQUENCE

OTP / OAuth authentication

Unauthenticated auth endpoints are internet-facing, but rate-limited. OTP state lives in Redis; successful verification creates/updates the user and returns short-lived access + rotated refresh tokens.

02 · SEQUENCE

Public search, venue details & availability

Venue discovery is public read data. Public responses use explicit DTOs so owner contact details, payout settings, internal notes and user PII never leave the private model.

03 · SEQUENCE

Create booking + hard slot lock

Availability display is advisory. The authoritative conflict check happens during booking creation using Redis for fast holds and Postgres uniqueness for correctness.

04 · SEQUENCE

Full payment checkout

The browser/provider redirect is UX only. Pitch TZ trusts the signed provider callback (or reconciliation) to decide whether the payment succeeded.

05 · SEQUENCE

Split payment booking

A split creates n ledger shares. Each share can be paid in-app or through a tokenized public QR page. The organizer can cover the remainder before cutoff.

06 · SEQUENCE

Tokenized public scan-to-pay

No account is required. The public session returns only masked booking context and the exact payable share; the session is rate-limited, expiring and single-purpose.

07 · SEQUENCE

Payment webhook + reconciliation

Money callbacks are idempotent and signature-verified. Webhook acknowledgement stays fast; receipts and non-critical work move to BullMQ.

08 · SEQUENCE

Installment payment

Installments are ordinary payment shares with due dates. Booking state remains part_paid until the required installment threshold is met.

09 · SEQUENCE

Cancellation + refund

Cancellation eligibility is computed server-side from venue policy, booking time and payment state. Refunds create reverse transactions; they never mutate the original successful charge.

10 · SEQUENCE

Owner manual / walk-in booking

Venue owners can reserve their own pitch for phone bookings or walk-ins, but they use the same hard conflict rules as customer bookings.

11 · SEQUENCE

Owner block / unblock slot

Blocks are first-class records and immediately invalidate availability caches. Blocking a slot that already has a confirmed booking is rejected unless an admin cancellation flow is used.

12 · SEQUENCE

Owner payout preference: daily or weekly

Payout cadence is configured per venue, because one owner can operate multiple venues with different cash-flow preferences.

12A · SEQUENCE

Daily owner payout

Daily payout improves owner cash flow without paying money that is still exposed to an unfinished booking or unresolved payment.

12B · SEQUENCE

Weekly owner payout

Weekly venues use the same payout engine; only the due-window calculation changes. This avoids maintaining two separate money systems.

13 · SEQUENCE

Team challenge → match booking

Read-only team profiles, fixtures and standings can be public; creating teams, joining and issuing challenges requires authentication.

14 · SEQUENCE

Review submission

Reviews are public read data, but only the customer from a completed booking can create one review for that booking.

15 · SEQUENCE

Venue owner application + admin approval

Owner onboarding is authenticated. Public discovery only exposes venues after status becomes active.

16 · SEQUENCE

Admin dispute resolution + refund

Disputes preserve evidence and audit history. Admin actions use finance/support scopes, and refunds still go through the same Payment Service and provider idempotency rules.

17 · SEQUENCE

Notification dispatch: push + email first

Transactional email is the low-cost durable channel; push handles instant UX. SMS is primarily OTP/critical fallback, while WhatsApp is optional for conversion-heavy invite flows.

18 · SEQUENCE

Public city waitlist + launch notification

Waitlist sign-up is a public write endpoint protected with abuse controls. It does not expose the waitlist itself.

Public response rule

Never serialize DB entities directly.

VenuePublicDTO:
 id, name, area, geo,
 rating, amenities,
 public rules, pitches,
 photos, public extras,
 price summary

EXCLUDE owner_id/contact,
fee_rate, payout data,
internal/admin metadata.
Implementation principle: public discovery and private commerce share domain services but not response contracts. The provider redirect never confirms money, daily/weekly payouts share one idempotent payout engine, and outbound communications use push/email as the normal path with SMS/WhatsApp reserved for cases where the extra cost has clear value.
